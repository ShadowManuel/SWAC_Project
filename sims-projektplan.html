Eure Tasks

Alle Aufgaben liegen als Issues auf unserem GitHub-Board „SIMS“. Jedes Issue hat eine Beschreibung, Akzeptanzkriterien, Testfälle und eine Definition of Done, also eine Checkliste, wann der Task wirklich fertig ist. Sobald die Rollen verteilt sind, weist euch eure Issues selbst zu und schiebt sie auf dem Board weiter, wenn ihr anfangt oder fertig seid. Welche Issues zu welcher Rolle gehören, steht unten unter „Rollen im Team“.

Umfang

  • Auth: Login prüft Benutzername und Passwort-Hash und gibt id, username und role zurück. User anlegen, deaktivieren, auflisten.
  • Tickets: Incident anlegen, bearbeiten, schließen, auflisten. Eskalation erhöht escalationLevel um eins.
  • Logging: Die anderen Services schreiben Log-Einträge, die Liste ist im Frontend sichtbar.
  • Frontend: Login, Incident-Liste und -Formular, User-Liste, Log-Liste.
  • Docker: alles startet mit docker compose up.
  • SAST: Semgrep-Lauf nach Angabe, Ergebnisse in der README.

Fertig, wenn: die Demo einmal komplett durchläuft. Ideen für später kommen nur in den Roadmap-Abschnitt der README.

Architektur

Drei kleine Microservices in ASP.NET Core (.NET 10). Jeder Service hat seine eigene Datenbank in einem eigenen Container. Auth und Tickets nutzen SQL Server, angelegt mit Entity Framework Code-First. Das Logging speichert in Redis. Jede Datenbank hängt in einem eigenen Netz, das nur ihr Service erreicht.

Durchgezogen: Aufrufe über HTTP bzw. zur Datenbank. Gestrichelt: Log-Einträge. Die APIs sitzen gleichzeitig im Netz app und im Netz ihrer Datenbank; keine API erreicht die Datenbank einer anderen.

Schnittstellen

Die Schnittstellen hier sind unser gemeinsamer Bauplan. Haltet euch beim Programmieren genau an die Feldnamen, Werte und Statuscodes, dann passen Frontend und APIs am Ende zusammen, auch wenn alle gleichzeitig daran arbeiten. Sobald ein Service läuft, seht ihr seine Endpoints auch unter /scalar und könnt sie dort direkt ausprobieren. Wenn ihr an einer Schnittstelle etwas ändern müsst, sagt es vorher in der Gruppe, weil das Frontend davon abhängt.

Es gibt keine Token. Soweit ich weiß, hat der Lehrer gesagt, dass wir keine brauchen. Falls das jemand anders verstanden hat, korrigiert mich gern. Das Frontend merkt sich nach dem Login id, username und role und blendet Admin-Funktionen für normale User aus. Wer die API direkt aufruft, kommt trotzdem an alles heran. Das kommt als bekannte Einschränkung in den Security-Abschnitt der README.

Regeln für alle Endpoints

  • JSON mit Feldnamen in camelCase: reporterName, nicht ReporterName.
  • Enums als Text: "High", nicht 3.
  • Zeitangaben als ISO 8601 in UTC: "2026-11-02T10:15:00Z".
  • Fehler immer als { "error": "Text für den User" }.
  • Passwort-Hashes verlassen nie den Auth-Service.

Reporter und Assignee

ReporterId und AssigneeId verweisen auf User aus der Auth-Datenbank. Weil die in einem anderen Container liegt, kann die Ticket-Datenbank keinen Foreign Key auf sie setzen. Sie sind deshalb normale Zahlen, die die Datenbank nicht prüft.

Damit die Incident-Liste Namen anzeigen kann, ohne für jede Zeile den Auth-Service zu fragen, speichert der Ticket-Service den Namen als Kopie in ReporterName und AssigneeName mit. Das Frontend schickt beides mit: beim Anlegen reporterId und reporterName des angemeldeten Users, beim Zuweisen assigneeId und assigneeName aus der User-Liste.

Diese Entscheidung kommt ins ER-Diagramm und in die README.

SAST mit Semgrep

Semgrep läuft wie in der Angabe beschrieben als Docker-Container über das Repo. Dev D testet den Befehl am Anfang, lässt ihn nach Tag 8 auf dem fertigen Code laufen und bereitet die Ergebnisse für die README auf.

Befehl (im Repo-Ordner, PowerShell)

docker run --rm -v "${PWD}:/src" returntocorp/semgrep semgrep --config auto

In die README kommen: Anzahl der Findings, die wichtigsten davon und was damit passiert ist (behoben oder begründet, warum nicht).

Arbeitsregeln

  • main ist immer lauffähig: Wer main pullt und docker compose up --build ausführt, bekommt alle Container ohne Fehler gestartet. Deshalb vor jedem Merge main in den eigenen Branch pullen, alles starten und prüfen, dass alle Container laufen. Halbfertige Features sind okay, ein Service, der beim Start abstürzt, nicht.
    Warum: Alle pullen jeden Tag main. Ist main kaputt, kann niemand mehr seinen eigenen Teil testen, auch wer selbst nichts falsch gemacht hat. Deshalb gilt: Ist main doch kaputt, wird zuerst repariert oder der Merge mit git revert zurückgenommen, bevor jemand weiterarbeitet.
  • Kurze Branches: Ein Branch pro Task, höchstens 1–2 Tage alt. Jeden Tag main in den eigenen Branch pullen.
    Warum: Je länger ein Branch lebt, desto weiter entfernt er sich von dem, was die anderen auf main ändern, und desto mehr Merge-Konflikte gibt es am Ende. Viele kleine Merges sind viel einfacher als ein großer.
  • Task-Kürzel überall: Branch, Commits und Pull Request beginnen mit dem Kürzel aus dem Issue.
    • Branch: A3-login
    • Commit: A3: Login-Endpoint hinzugefügt
    • Pull Request: Titel A3: Login, in der Beschreibung Closes #7
    Warum: So sieht man auf einen Blick, zu welchem Task eine Änderung gehört. Mit Closes #… wird das Issue beim Merge automatisch geschlossen und wandert auf dem Board auf „Done“.
  • Pull Requests: Nichts direkt auf main pushen, jede Änderung kommt über einen Pull Request. Wer die Prüfung oben gemacht hat, mergt seinen PR selbst. Wenn ihr unsicher seid, markiert mich im PR.
  • Getestet wird über docker compose up, nicht nur in Visual Studio.
  • Wer eine Security-Maßnahme einbaut (Hashing, Validierung, EF statt SQL-Strings), schreibt sie in einer Zeile in den Security-Abschnitt der README.
